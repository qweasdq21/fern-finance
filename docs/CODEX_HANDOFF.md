## 4. 已确定的业务配置

### 项目

初始创建：
- 个人
- OCL
- 上班（LEBREW）
- 打火机套大作战（坏苹果）
- 临时

WING 是 OCL 的其中一个产品，不应默认提升为独立顶级项目。用产品维度或子项目表达，具体形式可在深度修改时确定。

用户要求允许新建和删除项目，并要求敏感项目操作输入密码。现有代码只实现项目名称编辑。删除历史引用项目应保留流水归属，优先设计归档或受控删除，不可直接丢失账务关联。

不自动把工作公司的全部账或第三方账户纳入私人账本，也不预建用户已明确不需要的公司及香港公司账户。用户管理的 OCL 资金仍在本系统范围内。

### 账户与币种

- 允许增加其他银行卡。
- 可管理现金、微信、支付宝、银行账户、PayPal、Shopify 等实际资金位置。
- PayPal 和 Shopify 默认美元 USD，其他默认人民币 CNY。
- 「Shopify」应根据真实资金路径区分销售渠道、待结算资金与实际收款账户，不能把同一笔钱重复算在 Shopify 和 PayPal。
- 各账户币种与默认值应可配置；具体真实余额由用户录入，不能使用演示值。
- 跨币种业务需保留原币金额、收付款金额、汇率和手续费；只有明确汇率及基准日期时才可汇总成本位币。

### 往来与负债

范围包括欠款、借款、供应商代付款、信用卡还款、借贷平台和创业项目资金周转。界面必须明确区分：
- 借入：我/当前项目欠别人。
- 借出：别人欠我/当前项目。

还应支持往来双方、所属项目、本金、剩余本金、部分还款、到期日、状态及历史记录。利息和手续费与本金分开。

## 5. 用户明确纠正过的账务规则

### 账户内部转账

例如支付宝转微信、微信转银行卡。这是同一笔资金换位置：转出账户减少、转入账户增加，记录去向，不计收入或支出。

不能只保存一条带 toAccountId 的记录而不更新两端余额。两端变动要一起成功或一起失败。

### OCL 正常付款与报销

用户说 OCL 的资金由自己掌握，直接由 OCL 资金承担业务费用时，只需记录 OCL 的支出。操作人是用户，不代表付款必然是「个人垫付」。

若个人自己的钱实际垫付项目支出，则需要区分业务归属与付款来源：
- 业务支出归项目。
- 个人账户现金减少。
- 项目形成对个人的应付款。
- 后续项目报销：项目账户减少、个人账户增加，应付款结清，不再生成第二次支出。

### 项目借给个人或其他项目

用户：「我有时会借用其他项目钱到个人支持或者其他项目，需要记一笔我欠哪个项目。」

例如 OCL 借给个人：
- 记录资金从哪个账户流向哪个账户。
- OCL 有应收、个人有应付。
- 借款不是经营收入或支出。
- 归还本金减少该往来余额，也不是经营收入或支出。

钱在同一物理账户内、仅项目资金归属发生变化时，不能制造虚构银行转账；应记录归属和项目往来变化。

### 资本投入、贷款与业务收支

前一轮提出的模型建议是分别识别资本投入与应归还的借款，不能凭借转入转出方向决定是否为收入支出。这个区分是合理的重构建议，具体表单和字段尚未实现。

### 信用卡

信用卡消费形成项目/个人支出及信用卡负债；还款本金减少付款账户和信用卡负债，不重复记支出。手续费、利息独立记支出。期初信用卡欠款是期初负债。

### 期初与资产

启用日之前的账户余额、已有资产、借出应收及借入欠款，作为期初状态。不能把「目前有多少钱」当成本期收入。

设备等资产需要区分购入现金流、资产存量和经营损益；相关完整资产模块在原型中尚未实现。

## 6. 图片与自然语言录入

用户明确要求：
- 单张或批量图片。
- 为图片添加自然语言注释，系统识别并分类。
- 不要求每笔识别结果先弹人工确认。
- 无法识别留空，集中在每周核对时补充。

「不需要确认」不等于可以猜测金额或账户。建议：
- 原图与注释持久保存，保留来源关联。
- 可确定且满足入账条件的事件自动入账，显示结果。
- 缺乏必要金额、账户、往来方等内容的事件保存为待补充记录，不参与有效余额与损益。
- 字段可追溯到识别结果，用户可修改。
- 批量导入有进度、每项成功/失败结果、可重试和重复识别。
- API 重试及重复图片不能形成重复有效入账。
- 金额未知时应为 null/待补充，不用 0 假装识别成功。

## 9. 当前源码核对结果

技术栈：
- React 19，TypeScript，Next API 兼容层 vinext。
- Vite 8，Tailwind CSS，shadcn/Base UI。
- Cloudflare Worker、D1、Drizzle，Sites 元数据及 R2 绑定。
- Node.js >=22.13.0。
- 部分脚本依赖 Bash/Linux 的 flock、curl、GNU timeout；Windows 建议 WSL，macOS 需检查脚本兼容，不能承诺原命令跨平台直接执行。

核心文件：
- app/page.tsx：保护主页并加载 FinanceDashboard。
- app/chatgpt-auth.ts：从平台注入的请求头解析用户。
- components/finance-dashboard.tsx：主要界面和客户端表单。
- app/api/finance/route.ts：GET/POST/PATCH，按 ownerEmail 过滤顶层数据。
- db/schema.ts：projects/accounts/transactions/debts/attachments/settings。
- db/index.ts：D1 连接。
- drizzle/：迁移与快照。
- vite.config.ts、worker/index.ts、.openai/hosting.json：运行与 Sites 配置。

本次从源码确认的缺陷：
- 总资产、现金、净现金流、待收待付和图形含硬编码演示数据。
- 初始 transactions 为 seed，服务器返回空列表时仍显示示例；请求失败被静默吞掉。
- API 录入交易仅插入 transactions，没有余额增减、项目资金调整或债权债务联动。
- transactions 上虽然有 accountId、toAccountId、sourceProjectId、targetProjectId，但这些字段不是完整账务引擎。
- 入账仅检查 amount/kind 是否 truthy，缺少完整金额、枚举、关联对象归属和字段校验。
- POST 对传入的项目/账户 ID 需要验证同属当前用户，不能仅靠结果查询按 ownerEmail 过滤。
- PATCH 修改交易主要为金额、备注、分类；未联动余额、往来、类型、账户、项目、日期和币种。
- 项目详情只能修改名称，缺少资金明细、产品/子项目和归档流程。
- 账户虽保存 openingBalance/currentBalance，流水不更新它们；直接改 currentBalance 缺少调整记录和一致性规则。
- debts 与现金流水各自独立；修改 outstanding 不是有历史记录的还款。
- 图片只是客户端计数/提示，未实现实际 OCR 或持久附件上传。
- saveCapture 从注释匹配首个数字，并把「还款」等词判为 expense；无法支持正确往来逻辑。
- 流水展示所属项目是固定「已入账」，不是 projectId 对应名称。
- money() 固定人民币符号，没有真实多币种显示。
- GET 只取最新 100 条 transactions，不能用它来计算全量余额或完整报表。
- GET 在没有项目时同时插 settings；settings.ownerEmail 为 unique，全部项目为空的重新初始化可能产生冲突。
- 日期部分使用 UTC ISO，界面有固定日期，需要按用户时区统一。
- 报表和设置存在占位页；不能宣称功能已交付。
- schema 的金额使用 real；深度重构应评估整数分或精确 decimal，避免浮点累计误差。
- 缺少完整资产、业务事件、账务分录、往来清偿、批量导入和对账模型。

## 10. 前一轮提出的重构方案（尚未实施）

分开以下模型：
1. 账户：资金位置及原币余额。
2. 项目/资金归属主体：个人与各项目。
3. 分类和产品：业务用途、OCL/WING 等维度。
4. 业务事件：收入、支出、账户转账、项目借贷、代付、报销、还款、期初、调整等。
5. 账务分录/余额变动：事件对账户、项目和往来的全部影响。
6. 债权债务：债权人、债务人、来源、币种与剩余本金。
7. 还款/清偿关联：一笔或多笔部分结清及其现金来源。
8. 附件、识别任务、待补充字段、导入批次与审计历史。

所有变化由业务事件统一产生，可重新计算，不依赖互不一致的手填余额。每笔事件的多处影响需要原子提交；同一事件只允许入账一次。正式修改用可追溯的撤销/更正方式，防止余额漂移。

这是设计方向，不要求未经当前技术约束分析就机械引入某种会计架构。项目归属往来与所有账户资产的合并报表要区分，内部债权债务合并时不能重复抬高总资产。

| 重复提交 | 同一事件 ID 提交两次 | 只生成一笔有效事件及一套分录 |
| 待补充图片 | 金额无法识别 | 保存图片和待补充记录，不改变有效余额 |
| 批量部分失败 | 3 张图，1 张不支持 | 可查看每项结果，失败可重试，成功项不重复入账 |
| 美元与人民币 | PayPal USD 20、现金 CNY 100 | 分币种显示，未指定汇率时不能显示「总额 120 元」 |
| 非本人对象 | 提交另一个用户的 accountId/projectId | 拒绝写入，不能跨用户关联或读写 |
| API 故障/空账本 | 请求失败或列表为空 | 显示明确错误/空状态，不回填演示财务数据 |
